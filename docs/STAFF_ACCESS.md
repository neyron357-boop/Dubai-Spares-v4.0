# Доступ сотрудников и публичных клиентов

В существующем развёртывании `VITE_REQUIRE_AUTH=false`. Подготовленные изменения не применяют SQL и не создают пользователей в чужом Supabase автоматически. Доступ к GitHub не является административным доступом к Supabase.

## Порядок включения

1. Сделать резервную копию Supabase и локальный экспорт приложения. На время переключения остановить изменения рабочих заказов.
2. Проверить фактическую структуру таблиц, views, функций и Storage policies в Supabase. Миграция рассчитана на схему этого репозитория и PostgreSQL 15+; сначала выполнить её на копии базы.
3. В Supabase Authentication создать учётные записи владельца и сотрудников. Отключить самостоятельную регистрацию, если она не нужна. Использовать безопасные пароли.
4. Выполнить `supabase/migrations/20260930_staff_access.sql` через административный SQL Editor. Она включает RLS, заменяет старые политики доступа приложения и создаёт RPC. Не удаляет заказы, варианты, поставщиков или лиды.
5. Добавить UUID разрешённых пользователей:

   ```sql
   insert into public.app_members(user_id)
   values ('UUID_СОТРУДНИКА_ИЗ_AUTH_USERS')
   on conflict do nothing;
   ```

6. Проверить, что строка `app_state.public_settings` содержит только публичные контакты, условия и реквизиты. Не хранить в ней внутренние настройки или секреты. Доступ к `global` для анонимного клиента закрывается.
7. В GitHub → Settings → Secrets and variables → Actions → Variables установить `REQUIRE_STAFF_AUTH=true`. Перезапустить Deploy application to GitHub Pages. Локально — `VITE_REQUIRE_AUTH=true` в `.env.local` и перезапуск Vite.
8. Проверить вход владельца, отказ для постороннего пользователя, создание/изменение/чтение заказов, загрузку фото, отправку публичного лида, чтение клиентской ссылки и истечение её срока.

## Что защищает миграция

- Рабочие таблицы доступны только пользователям из `app_members`. Обычная регистрация в Supabase не даёт доступ.
- Рабочие views используют `security_invoker`, чтобы не обходить RLS.
- Публичное предложение читается через `public_quote_by_token`: только совпадающий токен длиной не менее 32 символов и только до `expires_at` по серверному времени. Публичный клиент не перечисляет таблицу предложений и не изменяет её при чтении.
- `public_lead_create` сохраняет лид, проверяет основные ограничения и ключ идемпотентности; повтор не переписывает существующий лид. Публичный клиент не получает список лидов и не создаёт рабочие заказы напрямую.
- Публичный клиент может добавить новое фото к лиду, но не получает UPDATE/DELETE на чужие изображения. Сотрудники управляют изображениями своего приложения.

## Границы

Эта модель рассчитана на одну компанию с общей рабочей базой. Это не изоляция нескольких организаций. Локальные данные остаются на доверенном устройстве после выхода; на общих компьютерах нужны отдельные профили браузера и осознанный сброс после экспорта. Нельзя использовать локальный пароль или скрытый интерфейс вместо серверных прав.

Изображения в текущей схеме используют публичные buckets. URL уже опубликованного изображения доступен любому, кто его знает. Для конфиденциальных документов нужны private buckets, отдельное хранение, короткие signed URLs и серверная проверка доступа; простое включение RLS не делает публичные файлы приватными.

Нужно проверить все существующие Storage policies: дополнительные permissive policies вне известных имён могут расширять доступ. Серверная защита от массовой отправки публичных лидов/фото и CAPTCHA требуют отдельного управляемого endpoint. Рабочая Edge Function AI также должна проверять JWT и членство на сервере; её исходников нет в репозитории.

Нельзя отключать `REQUIRE_STAFF_AUTH`, чтобы обойти ошибку после включения RLS. Проверяйте учётную запись, членство, токен и миграцию. При проблеме восстановите совместимый релиз приложения, сохраняя серверную защиту.
