# Проверка качества — 30 сентября 2026

Цель: сохранить рабочие функции и данные, устранить обнаруженные дефекты, сделать проверки воспроизводимыми и запретить публикацию неисправной сборки. Дизайн сохранён; изменены элементы, мешавшие работе и доступности. Рабочие данные Supabase не изменялись.

## Исходное состояние

- 117 ошибок TypeScript в неиспользуемой вложенной копии исходников. Корневое приложение и вложенная копия расходились; поддерживались две версии кода.
- 13 известных уязвимостей npm: 6 high, 5 moderate, 2 low.
- Из 12 браузерных проверок проходили 10; две зависели от внешних данных или устаревшей разметки.
- Открытие публичной формы запускало очистку localStorage, sessionStorage, всех IndexedDB и кэшей origin.
- Восстановление IndexedDB могло удалять базу после неудачного чтения; очередь синхронизации удаляла изменения после нескольких ошибок.
- Карточка заказа, смета, счёт и публичная ссылка считали суммы по разным правилам. Скидка, количество и международное карго учитывались не везде.
- Счёт без явно переданного курса получал NaN. Чтение публичного предложения пыталось переписать его на сервере и могло отменить скидку.
- SQL bootstrap начинался с DROP TABLE CASCADE; полноценной серверной модели доступа сотрудников не было.
- В `.env.example` находился серверный ключ AI. Его удаление из текущего файла не отменяет прежнюю публикацию.

## Проверка

- TypeScript, lint на ошибки выполнения/правила hooks, production build.
- 25 unit-тестов: транзакции/сбои/повтор, резервные копии, деньги, документы, отмена и timeout AI.
- 14 браузерных сценариев: заказ/поиск, мобильные фильтры, фото, варианты, закупка, клиентские маршруты, сохранность данных при открытии публичной формы, экспорт и восстановление бэкапа с фото.
- 3 изолированных сценария доступа: сотрудник, посторонний пользователь, публичная форма.
- 2 теста push API: допустимые endpoint и ключи.
- npm audit frontend и API.
- SQL разобран PostgreSQL parser; это не замена применению и проверке политик на копии рабочей базы.

Браузерные тесты блокируют рабочий Supabase или используют имитацию сервера. Нет ложного утверждения, что эти тесты проверяют работу действующего облака. Автоматизация не доказывает отсутствие всех ошибок во всех ветвях большого приложения.

## Что требует внешнего доступа

1. Отозвать ранее опубликованный серверный AI-ключ у провайдера и заменить его в серверном окружении. Ключ остаётся в старой git-истории; новый секрет не должен попадать в клиент.
2. С административным доступом к Supabase проверить существующие данные/схему, создать пользователей, применить и проверить RLS-миграцию на копии базы, затем включить режим входа. До этого действующее приложение сохраняет прежнюю модель доступа; подготовленный экран входа не означает, что рабочая база защищена.
3. Проверить рабочую Edge Function `super-service`, её авторизацию, ограничения запросов и конфигурацию. В репозитории нет исходников этой функции. Push API и Telegram worker не размещаются на статическом GitHub Pages.
4. Решить требования к приватности файлов: текущие image buckets публичные. Для закрытых документов нужен отдельный серверный поток signed URLs.

При запросе рабочего Supabase из текущей среды сеть возвращала отказ прокси. Поэтому реальные операции записи, облачная синхронизация, AI и правила RLS на живой базе не проверялись и не изменялись. Административный токен или service-role нельзя присылать в чат или публиковать в репозитории; нужен подключённый безопасный канал управления проектом.
